# ADR 0017: Единый host просмотрщика материалов

## Статус

Принято.

## Контекст

Queryn хранит знания как обычные файлы. Пользователю нужна единая поверхность,
в которой можно изучить текст, код, структурированные данные, изображения,
PDF и контейнерные документы, не теряя положение в проекте. Просмотрщик поэтому
является частью основной модели продукта, а не набором несвязанных экранов для
отдельных расширений.

Текущая ветка desktop уже содержит базовые адаптеры и безопасный запасной путь.
Она подтверждает жизнеспособность подхода, но пока смешивает классификацию
типов, чтение файлов, выбор представления и пользовательские действия между
несколькими реестрами. При прямом наращивании форматов появятся расхождения в
поддерживаемых расширениях, ограничениях размера, поведении ошибок и правилах
безопасности.

Параллельно манифест расширения содержит будущий вклад `views`, который сейчас
валидируется, но не регистрируется и не отображается desktop-клиентом.
Произвольная загрузка интерфейса расширения внутрь основного renderer дала бы
ему доступ к состоянию приложения и резко расширила бы поверхность доверия.
Нужна более узкая модель расширения просмотрщика.

## Решение

### 1. Просмотрщик является host-поверхностью Queryn

Desktop предоставляет один `Material Viewer Host`. Он отвечает за выбор
адаптера, состояния загрузки, поиск, масштаб, навигацию, сохранение,
несохранённые изменения, повтор и безопасный запасной путь. Адаптер отвечает
только за представление конкретного материала и объявленный набор действий.

Пользователь не выбирает технический режим. Он открывает файл и получает
лучшее доступное представление. Если специализированный адаптер отсутствует,
не совместим или завершился ошибкой, host сохраняет метаданные и системное
открытие.

### 2. Обычный файл остаётся источником истины

Просмотрщик не создаёт скрытую копию документа как новую каноническую модель.
Базовая правка изменяет исходный поддержанный текстовый файл только после
явного сохранения. Производные миниатюры, индекс, извлечённый текст и фрагменты
таблиц являются кэшем и могут быть удалены.

Перед сохранением host проверяет, что исходный файл не изменился с момента
чтения. Конфликт не разрешается тихой перезаписью. Пользователь получает выбор
перечитать файл, сохранить копию или подтвердить замену после просмотра
различий. Кодировка и окончания строк сохраняются, если адаптер явно не
предлагает преобразование.

### 3. Классификация имеет одного владельца

`@queryn/project` владеет каноническим `FileTypeDescriptor` и чистой
классификацией материала. Main process собирает `FileTypeEvidence` из имени,
расширения, заявленного MIME, безопасной проверки сигнатуры и текстовой или
бинарной природы. Core возвращает тип, семейство представления, возможности,
уровень уверенности и признак несовпадения. Desktop и расширения не поддерживают
собственные полные копии таблицы типов.

Desktop main дополняет результат до `MaterialDescriptor`, который содержит
относительный путь, размер, версию файла, кодировку и разрешённые действия IPC.
Сырые байты сигнатуры, абсолютный путь и файловый дескриптор не передаются в
renderer.

Выбор представления выполняет реестр host на основе дескриптора и доступных
поставщиков. Он не доверяет одному расширению файла. Несовпадение расширения,
MIME и сигнатуры приводит к предупреждению и более безопасному адаптеру.

### 4. Привилегированное чтение остаётся в main process

Renderer не получает абсолютный путь проекта и не читает файл через Node.js.
Main process разрешает `projectId` и относительный путь, проверяет каноническую
границу проекта, символические ссылки, доступ, размер и допустимую операцию.
Чтение делится на ограниченные типизированные ответы:

- метаданные и дескриптор
- текстовый фрагмент с кодировкой и признаком усечения
- поток или страницы бинарного ресурса с ограничением размера
- производный результат безопасного парсера
- атомарное сохранение текста с проверкой версии исходника

Большой файл не передаётся целиком через IPC как строка или ссылка с данными.
Тяжёлый разбор выполняется в worker или отдельном процессе с ограничением
памяти, времени, глубины архива и объёма распаковки.

Бинарный ресурс выдаётся renderer как непрозрачный capability handle. Он
ограничен одним файлом, версией файла, допустимым диапазоном байтов, MIME,
суммарным бюджетом чтения и коротким сроком жизни. Handle отзывается при
закрытии материала, изменении файла или завершении окна и не раскрывает путь.

### 5. Встроенные адаптеры покрывают базовый учебный путь

Встроенный слой должен надёжно покрывать P0: Markdown, обычный текст, код,
JSON, XML, YAML, TOML, CSV, TSV, HTML как статический материал, изображения и
PDF. P1 включает Parquet, таблицы, документы, презентации и ноутбуки с
приближённым чтением без выполнения формул, макросов, ядер или сценариев.

Поддержка формата означает явный контракт точности и ограничений. Извлечение
текста из DOCX не называется точным отображением Word. Сетка XLSX не обещает
вычисление формул. Сохранённый вывод ноутбука показывается без запуска ядра.

### 6. Расширения добавляют поставщиков просмотра через узкий контракт

Будущий вклад называется `previewProviders`. Он является метаданными над
существующей зарегистрированной operation и не создаёт второй путь исполнения.
Viewer Host вызывает такую operation только через `OperationService`, поэтому
сохраняются project grants, risk policy, `JobManager`, отмена, таймауты,
ограничения ресурсов и структурированные ошибки.

Поставщик просмотра объявляет:

- namespaced идентификатор и версию контракта
- `operationId` существующей operation расширения
- поддерживаемые media types, расширения и сигнатуры
- приоритет и требуемый уровень уверенности классификации
- версию выходной host-схемы
- доступные действия host, включая поиск, навигацию и экспорт
- максимальный размер и возможность диапазонного чтения
- способ деградации при отсутствии зависимости

Связанная operation имеет `agentVisibility: "hidden"`, принимает один
материализованный файл, является идемпотентной и возвращает структурированный
документ по host-схеме. Viewer Host передаёт `OperationService` типизированный
`MaterialRef` с относительным путём и ожидаемой версией файла. `OperationService`
проверяет границу проекта и создаёт read-only snapshot в invocation input.
Сторонний runtime получает manifest snapshot и временный файл, но не исходный
путь проекта.

Operation не публикует артефакт без отдельного действия пользователя. Queryn
отрисовывает таблицу, дерево, страницы, текстовые блоки или миниатюры встроенными
компонентами. Это сохраняет тему, доступность, клавиатурное управление и единое
поведение ошибок.

Автоматический выбор допускается только для уже подключённого поставщика с
достаточными project grants. Remote и network runtime не получает содержимое при
простом открытии файла без сохранённого project-scoped разрешения или видимого
подтверждения получателя. До подтверждения используется встроенный fallback.

`contributes.views` не используется просмотрщиком. Произвольный сторонний UI не
входит в первый публичный контракт `previewProviders`. Если host-схем окажется
недостаточно, изолированная интерфейсная поверхность проектируется отдельным
ADR с одной выбранной границей Electron и отдельной моделью угроз.

### 7. Кэш просмотра является локальным производным состоянием

Извлечённый текст, миниатюры и фрагменты таблиц по умолчанию хранятся в данных
приложения, а не в папке проекта. Ключ кэша включает hash исходного файла,
идентификатор и версию поставщика, версию host-схемы и параметры разбора. Кэш
инвалидируется при изменении файла, имеет общий бюджет и может быть полностью
удалён без потери пользовательских данных.

Сохранение производного результата в проект выполняется отдельной operation
публикации артефакта по явному действию пользователя. Диагностический экспорт
не включает кэш просмотра по умолчанию.

### 8. Выбор поставщика детерминирован и объясним

Host сначала классифицирует материал, затем фильтрует совместимых поставщиков,
проверяет регистрацию operation, доступность runtime и разрешения, после чего
выбирает самый высокий приоритет. Встроенный безопасный адаптер всегда остаётся
последней ступенью.
Пользователь может увидеть название выбранного поставщика и выбрать другой
доступный вариант, но сохранённый выбор не должен блокировать файл после
удаления расширения.

Ошибка стороннего поставщика локализуется в области материала. Host фиксирует
контекст диагностики, предлагает повтор, переключение на встроенный адаптер и
системное открытие. Дерево проекта, другие вкладки и несохранённые изменения
не теряются.

### 9. Просмотр не выполняет содержимое

HTML, SVG, PDF, Office, ноутбуки и архивные контейнеры считаются потенциально
активным входом. Просмотрщик не запускает JavaScript, макросы, формулы с внешним
доступом, ядра, формы и сетевые запросы. XML-парсер не загружает внешние
сущности. Архивный разбор защищён от выхода за каталог, циклов, чрезмерной
глубины и распаковки несоразмерного объёма.

## Межрепозиторные границы

| Репозиторий | Ответственность |
| --- | --- |
| `queryn-spec` | Схема `previewProviders`, ссылка на operation, host-схемы результатов и коды ошибок |
| `queryn-core` | `FileTypeDescriptor`, классификация по нормализованным признакам и безопасные пути |
| `queryn-sdk` | Типы поставщика, тестовый набор и проверка манифеста |
| `queryn-runtime` | Запуск operation поставщика через общий flow, лимиты и производные результаты |
| `queryn-desktop` | `MaterialDescriptor`, Viewer Host, встроенные адаптеры, IPC, capability handles, кэш и взаимодействие |
| `queryn-extensions` | Эталонные поставщики сложных форматов без привилегий renderer |

## Последствия

Просмотрщик можно развивать как основной шлюз изучения проекта. Базовые
форматы останутся доступными без расширений, а специализированные парсеры смогут
добавляться без копирования оболочки и без полного доверия к интерфейсному коду.

Главная стоимость решения состоит в унификации текущих реестров, разделении
`FileTypeDescriptor` и `MaterialDescriptor`, проектировании host-схем и адаптации
общего operation flow к производному результату без обязательной публикации.

Текущая ветка является хорошей основой для встроенного слоя, но не завершённой
архитектурой расширений. До публичного `previewProviders` нужно стабилизировать
P0, общий реестр, capability handles, ограничения чтения, конфликт сохранения,
состояния ошибок и приёмочную матрицу. После этого контракт расширения
проверяется на реальных потребностях сложных форматов.
