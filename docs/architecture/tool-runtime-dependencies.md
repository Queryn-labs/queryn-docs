# Среды исполнения и зависимости инструментов

Эта страница разворачивает [ADR 0016](../adr/adr-0016-extension-runtime-dependencies.md)
в рабочую архитектуру. Она описывает, насколько устойчива текущая основа,
какие гарантии уже можно давать и что необходимо завершить до публичной
экосистемы расширений.

## Краткая оценка

Архитектурная основа устойчива на уровне разделения ответственности. Пакет,
установка, подключение к проекту, разрешения, операция, задание, runtime и
публикация артефакта уже являются разными сущностями. Это правильный каркас для
инструментов с разной природой.

Устойчивость пока ограничена на уровне поставки зависимостей. Система умеет
запустить заранее подготовленный процесс, контейнер или endpoint, но не имеет
полного общего контракта платформенной совместимости, подготовки среды,
управляемой загрузки и удаления языковых runtime. Поэтому текущую архитектуру
следует считать готовой для контролируемых встроенных и эталонных расширений,
частично готовой для сторонних самодостаточных пакетов и не готовой для
произвольной установки зависимостей из интернета.

## Что является стабильной основой

| Возможность | Состояние | Архитектурная оценка |
| --- | --- | --- |
| Extension Manifest v1 | Реализован | Подходит как входная декларация, требует расширения совместимости |
| Установка по версиям | Реализована | Правильная основа для отката и неизменяемости |
| SHA-256 файлов пакета | Реализован | Проверяет целостность, не доказывает автора |
| Установка отдельно от подключения | Реализована | Не позволяет пакету автоматически получить доступ к проекту |
| Project-scoped grants | Есть в runtime | Desktop пока выдаёт весь объявленный набор |
| Process, OCI, remote и MCP | Есть | Границы различаются правильно, зрелость драйверов неодинакова |
| Job Manager и публикация через outbox | Есть | Хорошая транзакционная граница результата |
| Модели как отдельные зависимости | Есть | Следует сохранить отдельно от пакетов расширений |
| Проверка handshake | Неполная | Ответ `initialize` должен стать обязательным условием готовности |
| Платформенные варианты | Неполные | Нужны схема, выбор артефакта и понятная причина несовместимости |
| Подготовка и удаление среды | Неполные | Нужны отдельные состояния, прогресс и сборка мусора |

## Целевая модель

```mermaid
flowchart LR
  Package["Неизменяемый пакет"] --> Verify["Проверка схемы, подписи и hash"]
  Verify --> Install["Установка версии"]
  Install --> Connect["Подключение к проекту и grants"]
  Connect --> Prepare["Проверка и подготовка runtime"]
  Prepare --> Handshake["initialize и совместимость"]
  Handshake --> Invoke["Запуск задания"]
  Invoke --> Ingest["Проверка outbox и публикация"]
  Prepare -.-> Unavailable["Структурированная недоступность"]
  Handshake -.-> Unavailable
  Unavailable --> Project["Остальной проект продолжает работать"]
```

В этом потоке нет шага, на котором код расширения самостоятельно меняет
системное окружение. Сетевая загрузка выполняется host-компонентом, имеет
заранее известный источник, размер, контрольную сумму, лицензию, прогресс и
возможность отмены.

## Контракт классов исполнения

### Builtin

`builtin` собирается и подписывается вместе с Queryn. Он может использовать
внутренние библиотеки приложения только в пределах версии поставки. Такой
runtime не является примером контракта для сторонних расширений. Вынесение
встроенной возможности в публичный SDK требует перехода на те же типы,
протокол и ограничения, которые доступны внешнему автору.

Валидатор стороннего пакета отклоняет runtime с `kind: "builtin"`. Такой
descriptor создаётся только при регистрации встроенных обработчиков host-кодом.

### Node process

`node-process` предназначен для переносимого JS runtime. Пакет обязан содержать
готовый собранный entrypoint, включённые в сборку производственные зависимости
и относительные ресурсы. Каталог `node_modules`, рабочее дерево автора, PATH
разработчика и глобальные пакеты не входят в контракт поставки. Host запускает
совместимую версию Node.js с ограниченным окружением и отдельными каталогами
input, work и outbox.

В манифесте нужны диапазон engine, поддерживаемые платформы, ожидаемый протокол,
лимит памяти и оценка места. При несовместимости host не пытается исправить
пакет командой package manager. Он возвращает стабильный код и предлагает
установить совместимую версию расширения.

Пакет содержит машинно читаемый состав производственных компонентов и лицензий.
Упаковщик и установщик ограничивают число файлов, размер отдельного файла,
общий размер декодированного содержимого и итоговый объём установки. Проверка
происходит до materialization, чтобы JSON-пакет с base64 не мог вызвать
неограниченное потребление памяти или диска.

### Несколько runtime в одном расширении

Манифест содержит массив runtime descriptors. Один descriptor выбирает один
`kind`, но расширение может сочетать локальный parser process, OCI-операцию и
удалённый connector. Каждый contribution с исполнением указывает `runtimeId`.
Регистрация отклоняется при отсутствующей, неоднозначной или несовместимой
ссылке. Разрешения и готовность вычисляются отдельно для каждого descriptor,
поэтому отказ одного runtime не отключает остальные возможности пакета.

### Native process

`native-process` используется для самодостаточных программ. Один пакет может
содержать таблицу платформенных артефактов. Каждый артефакт имеет собственные
путь, архитектуру, hash, размер и необязательный минимальный выпуск ОС. Выбор
делает host до выдачи разрешения на исполнение.

Динамическая зависимость от системной библиотеки допустима только при явной
проверке. Если библиотеку нельзя надёжно обнаружить и объяснить пользователю,
пакет должен быть собран статически или переведён на OCI. Автоматическая
установка системной библиотеки из desktop-клиента не входит в модель.

### OCI

OCI подходит для тяжёлых парсеров, научных библиотек и инструментов со сложным
нативным окружением. Образ закрепляется полным digest. Host проверяет наличие
движка, загружает образ отдельным подготовительным заданием и запускает
контейнер без корня проекта, сокета движка, root, capabilities и сети по
умолчанию.

Контейнер получает только материализованные входы, временную работу, outbox и
разрешённый кэш моделей. Ограничения CPU, RAM, времени и объёма файлов являются
частью invocation. Отсутствие Docker или другого совместимого движка делает
операции этого runtime недоступными, но не повреждает проект.

### Remote и MCP

Удалённый runtime не устанавливает вычислительные зависимости на устройство.
Он добавляет зависимость от сети, внешнего оператора и его политики хранения.
Endpoint, протокол, способ аутентификации и получатель данных должны быть
видимы до подключения.

Loopback endpoint проверяется как локальное подключение, но не получает статус
встроенного доверенного кода. MCP адаптируется к общей модели операций, риска,
заданий и результатов. Он не обходит разрешения и публикацию артефактов.

## Будущий контракт зависимостей

Если Queryn добавит управляемые Python, Java или другие среды, запись
зависимости должна быть декларативной и адресуемой по содержимому. Минимальный
контракт включает:

| Поле | Смысл |
| --- | --- |
| `id` | Стабильный идентификатор поставщика и семейства среды |
| `version` | Точная версия подготовленного runtime |
| `platform` и `arch` | Целевая платформа |
| `source` | Проверяемый источник загрузки |
| `sha256` | Контрольная сумма архива |
| `sizeBytes` | Ожидаемый объём загрузки |
| `unpackedSizeBytes` | Верхняя граница места после распаковки |
| `license` | Идентификатор и ссылка на условия |
| `entrypoints` | Разрешённые бинарные точки запуска |
| `environment` | Белый список переменных, которые задаёт host |

Lock проекта не должен хранить абсолютный локальный путь такой среды. Он
закрепляет логическую версию. Физическая установка принадлежит устройству и
может совместно использоваться несколькими проектами после проверки hash.

## Состояния и ошибки

Установка, подключение, подготовка и исполнение являются ортогональными
состояниями. Их нельзя хранить одним полем статуса.

| Область | Ключ | Примеры состояний | Что видит пользователь |
| --- | --- | --- | --- |
| Пакет | extension id и version | `installed`, `integrity-error`, `incompatible` | Сохранённая версия, происхождение и совместимость |
| Проект | project id и extension id | `disconnected`, `connected`, `blocked` | Закреплённая версия и grants этого проекта |
| Подготовка | runtime id, version, platform и arch | `not-prepared`, `preparing`, `ready`, `unavailable` | Загрузка, объём и причина недоступности |
| Исполнение | runtime id и lifecycle scope | `stopped`, `starting`, `running`, `stopping`, `failed` | Активный процесс и возможность перезапуска |

Operation доступна только при установленной совместимой версии, подключении к
проекту, достаточных grants, готовой среде и успешной policy evaluation. UI
может показывать одно итоговое состояние операции, но runtime хранит исходные
состояния раздельно.

Минимальный набор кодов должен различать несовместимую платформу, отсутствующий
движок, нехватку места, ошибку загрузки, несовпадение hash, отказ в разрешении,
ошибку handshake, аварийное завершение процесса и превышение ресурса.

## Границы безопасности

Установка, подпись и sandbox решают разные задачи. Подпись подтверждает
издателя. Hash подтверждает неизменность. Разрешения ограничивают заявленные
возможности. Изоляция уменьшает последствия вредоносного кода. Ни один слой не
заменяет остальные.

Секреты передаются через host API и только для конкретного получателя. Они не
становятся переменными окружения всего приложения. stdout зарезервирован под
протокол процесса. stderr ограничивается, маркируется источником и хранится в
диагностическом журнале после очистки.

## Последовательность внедрения

1. Сделать проверку `initialize` обязательной и добавить тесты несовместимой
   версии протокола.
2. Добавить в спецификацию платформу, архитектуру и engine requirements.
3. Разделить package, project connection, preparation и execution state в
   runtime RPC.
4. Показать в desktop причину недоступности и подготовку с прогрессом.
5. Запретить runtime-установку package manager и проверить самодостаточность
   эталонного `node-process` пакета.
6. Ограничить формат пакета по числу файлов, размеру и составу зависимостей.
7. Зарезервировать `builtin` для host и проверить несколько runtime одного пакета.
8. Добавить платформенные варианты нативного пакета и их выбор.
9. Реализовать управляемое удаление и сборку неиспользуемых зависимостей.
10. Проектировать общие языковые среды только после появления минимум двух
   реальных расширений с одинаковой потребностью.

## Критерии готовности публичной экосистемы

Архитектура готова к сторонним пакетам, когда установка не выполняет их код,
вся совместимость проверяется до задания, любая загрузка объяснима до начала,
удаление освобождает принадлежащие данные, нарушение целостности локализуется на
одной версии, а отсутствие зависимости не мешает открыть проект.
