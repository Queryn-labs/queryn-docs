# ADR 0018: Структурированные ошибки и диагностика

## Статус

Принято.

## Контекст

Queryn пересекает несколько границ: проектную библиотеку, desktop IPC,
локальный runtime RPC, процессы расширений, OCI, MCP и поставщиков моделей.
Строка исключения теряет смысл при прохождении этих границ. Renderer не может
понять, можно ли повторить действие, пользователю показывается технический
текст, а разработчик не может связать сбой интерфейса с заданием и процессом.

Особенно вредно смешивать `stderr` внешнего процесса с сообщением ошибки.
`stderr` может содержать многострочный отладочный вывод, путь, данные сторонней
библиотеки или секрет. Он полезен в защищённом журнале, но не является
пользовательским объяснением и не должен менять программную классификацию
сбоя.

Полностью выключенные журналы делают редкие сбои невоспроизводимыми. Постоянный
подробный режим создаёт риск утечки содержимого проектов и бесконтрольного
роста данных. Нужна двухуровневая диагностика с безопасным базовым журналом и
временным расширенным сбором по явному согласию.

## Решение

### 1. Ошибка является версионированным структурированным объектом

Все публичные границы используют единый конверт ошибки:

```ts
type JsonValue = null | boolean | number | string | JsonValue[] |
  { [key: string]: JsonValue }

interface QuerynFailure {
  schemaVersion: "1"
  code: string
  category: "validation" | "not-found" | "conflict" | "permission" |
    "compatibility" | "dependency" | "resource" | "timeout" |
    "external" | "internal"
  message: string
  retryable: boolean
  errorId: string
  traceId: string
  params?: Record<string, JsonValue>
}
```

`code` является стабильным машинным идентификатором. `category` задаёт общее
поведение интерфейса. `message` содержит безопасное человекочитаемое объяснение
для случая, когда клиент не знает код. `retryable` отражает допустимость
повтора, а не обещание успеха. `errorId` уникально определяет конкретную ошибку.
`traceId` связывает её с пользовательским действием, заданием и событиями между
процессами. `params` содержит только поля, разрешённые схемой конкретного кода.
Произвольные объекты подробностей не проходят через публичную границу.

Доступные действия восстановления не приходят от источника ошибки. Доверенный
host вычисляет их по `code`, текущему состоянию, выданным разрешениям и
идемпотентности операции. Сторонний runtime не может предложить выдачу
разрешения, запуск программы или сетевой переход.

Технический стек, необработанный `stderr`, токен, секрет, полный запрос модели и
содержимое файла не входят в конверт. Внутренняя цепочка причин сохраняется в
журнале под тем же `errorId` и `traceId`.

### 2. Коды принадлежат домену, а не экрану

Коды группируются по владельцу и причине, например:

- `PROJECT_PATH_OUTSIDE_ROOT`
- `PROJECT_FILE_CHANGED`
- `VIEWER_FORMAT_UNSUPPORTED`
- `VIEWER_PARSE_FAILED`
- `EXTENSION_INCOMPATIBLE_PLATFORM`
- `EXTENSION_DEPENDENCY_MISSING`
- `RUNTIME_HANDSHAKE_FAILED`
- `RUNTIME_PROCESS_EXITED`
- `POLICY_PERMISSION_DENIED`
- `MODEL_PROVIDER_UNAVAILABLE`

Desktop локализует известный код и подставляет только разрешённые параметры.
Новая версия runtime может вернуть неизвестный старому desktop код. В этом случае
показывается `message`, сохраняется `errorId` и доступно копирование номера
ошибки. Неизвестный код не превращается автоматически в системную аварию.

### 3. Перевод через RPC и IPC сохраняет семантику

Runtime помещает конверт в `error.data.querynFailure` JSON-RPC. Зарезервированные
числовые коды JSON-RPC продолжают описывать parse error, invalid request, method
not found и другие ошибки транспорта. Доменные ошибки используют выделенный
диапазон application error и строковый `code` внутри `querynFailure`.

Desktop main проверяет схему, удаляет неожиданные поля и передаёт типизированную
ошибку через preload. Renderer не разбирает текст через регулярные выражения и
не принимает решения по фрагментам английского сообщения.

Первый доверенный слой, который понимает доменную причину, создаёт `errorId` и
назначает `code`. Точка входа пользовательского действия или задания создаёт
`traceId`. Все последующие слои сохраняют оба идентификатора. Ошибка валидации
входа остаётся ошибкой валидации после прохождения runtime и IPC.

Сторонний runtime не считается доверенным источником пользовательского текста.
Host сопоставляет его ограниченный протокольный код с доверенным Queryn code.
Текст стороннего ответа сохраняется только как ограниченная диагностическая
подробность. Пользовательское объяснение формирует Queryn.

### 4. Асинхронные состояния сохраняют структуру ошибки

`JobDescriptor`, `RuntimeState`, состояние агентного запуска и другие публичные
асинхронные объекты используют поле `failure?: QuerynFailure`. Строковое поле
`error` читается для совместимости с ранее сохранёнными производными записями,
но не создаётся новой версией runtime. Миграция производных jobs выполняется при
загрузке и не изменяет пользовательские файлы проекта.

Пользовательская отмена представляется статусом `cancelled` без `failure`.
Неудачная отмена, аварийное завершение и восстановление после прерывания получают
собственный код. Успешное, отменённое и неуспешное завершение не смешиваются в
одной категории ошибок.

### 5. Базовые структурированные журналы работают всегда

Queryn постоянно пишет ограниченный локальный журнал событий, необходимый для
восстановления и диагностики. Запись содержит время, уровень, компонент,
стабильное имя события, `traceId`, необязательный `errorId` и только необходимые
идентификаторы. Где возможно, используются `jobId`, `sessionId`, `extensionId`, `runtimeId` и
локальный непрямой идентификатор проекта.

По умолчанию журнал не содержит:

- содержимое файлов и заметок
- полный путь проекта и имя пользователя в системном пути
- запросы и ответы модели
- секреты, токены и заголовки авторизации
- полный ввод и вывод операции
- необработанный дамп окружения

Пути сокращаются или заменяются идентификаторами. Поля проходят централизованную
очистку. Журналы имеют ограничение размера, ротацию, срок хранения и отдельные
каналы desktop, runtime и сторонних процессов.

### 6. Вместо глобального отладочного режима используется временная диагностика

Постоянный переключатель, который включает максимум данных для всего
приложения, не вводится. В настройках доступна временная расширенная диагностика
на ограниченный срок и область: один компонент, одно расширение, один runtime
или воспроизведение конкретного действия.

Перед включением пользователь видит, какие дополнительные данные могут быть
собраны. Режим автоматически выключается по сроку, после перезапуска или после
завершения выбранного сценария. Поля секретов очищаются всегда. Содержание
проекта включается только отдельным явным согласием и не требуется для обычного
диагностического пакета.

Для разработчика сохраняется переменная запуска и консольный уровень
журналирования. Она влияет на локальную среду разработки, но не является
единственным способом получить поддержку в пользовательской сборке.

### 7. Диагностический пакет создаётся прозрачно

Экспорт формирует архив через системный диалог сохранения. До сохранения Queryn
показывает состав и позволяет исключить необязательные разделы. Базовый пакет
содержит:

- версии Queryn, протоколов и схем
- операционную систему и архитектуру
- доступность контейнерного движка и модельных runtime без секретных настроек
- список расширений с версиями, состоянием и кодами совместимости
- последние очищенные ошибки по выбранным `errorId` и связанные события по
  `traceId`
- состояние прерванных заданий и восстановления
- описание включённых и исключённых категорий данных

Проектные файлы, запросы модели и credentials по умолчанию не включаются.
Пакет получает собственный manifest с версией формата и правилами очистки.

### 8. Интерфейс объясняет сбой и сохраняет путь продолжения

Пользовательское сообщение отвечает на три вопроса: что не удалось, что
осталось сохранным и какое действие доступно. Для ожидаемых ошибок интерфейс
показывает локальное состояние рядом с материалом, заданием или расширением.
Глобальное уведомление используется только для сбоя, который действительно
затрагивает всю рабочую область.

Кнопки `Повторить`, `Открыть системой`, `Проверить зависимость`, `Выдать
разрешение`, `Перезапустить runtime` и `Скопировать номер ошибки` вычисляются
host по `category`, `code`, текущему состоянию и политике. Наличие
`retryable: true` не запускает автоматический повтор операции с внешним
эффектом.

## Межрепозиторные границы

| Репозиторий | Ответственность |
| --- | --- |
| `queryn-spec` | Схема `QuerynFailure`, реестр публичных кодов, диапазон JSON-RPC и миграция Job Descriptor |
| `queryn-core` | Базовые типы, фабрики ошибок и очистка доменных подробностей |
| `queryn-sdk` | Ошибки автора расширения и безопасные протокольные ответы |
| `queryn-runtime` | `errorId`, `traceId`, миграция jobs, связь событий, журналирование, ротация и диагностика процессов |
| `queryn-desktop` | Локализация, действия восстановления, временный режим и экспорт |
| `queryn-extensions` | Проверки корректного поведения стороннего runtime при сбоях |

## Последствия

Человекочитаемые ошибки становятся частью архитектуры, а не текстом конкретной
кнопки. Команда сможет связывать сбой через процессы без передачи содержимого
проекта. Пользователь получит объяснимое восстановление вместо необработанного
JSON или `stderr`.

Цена решения состоит в ведении реестра кодов, миграции существующих строковых
ошибок и проектировании очистки данных. Полная типизация каждого внутреннего
исключения не требуется сразу. Миграция начинается с публичных границ и
наиболее частых сценариев, а неизвестные исключения переводятся в
`INTERNAL_UNEXPECTED` с `errorId` и `traceId`.

Текущая реализация соответствует решению частично. У runtime уже есть события,
jobs и диагностический RPC, но сообщения неоднородны, необработанный вывод
процессов может смешиваться с ошибками, а desktop показывает часть диагностики
как технический JSON. До завершения нужны схема, реестр кодов, корреляция,
очистка журналов, пользовательские состояния и проверяемый экспорт.
