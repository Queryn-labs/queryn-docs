# Участие

Изменения должны сохранять Osnova небольшой, local-first и понятной.

## Документация

- Пишите краткий Markdown.
- Не добавляйте спекулятивные детали реализации.
- Используйте ADR для решений, которые затрагивают больше одного репозитория.
- Сохраняйте имена репозиториев и контракты согласованными со спецификацией.

## Код

- Используйте TypeScript для общих пакетов и desktop-кода.
- Делайте API явными и типизированными.
- Добавляйте тесты для формата проекта, manifest и validation behavior.
- Не вводите cloud-зависимости в основные project flows.

## Гигиена комментариев

Комментарии должны объяснять решение или инвариант, когда это нельзя надежно выразить именем, типом или структурой кода. Плотность комментариев не нормируется. Каждый комментарий проходит обычное ревью на точность, актуальность и связь с кодом.

### Язык

Комментарии, JSDoc и шапки в `.ts`, `.tsx` и `.mjs` пишутся только на английском. Русский используется в UI-строках, документации `osnova-docs`, ADR, спеках и README.

Для сгенерированных файлов шапка берется только из шаблона `osnova-spec/scripts/generate-contracts.mjs` и пишется на английском. Ручное редактирование сгенерированных файлов запрещено. Это проверяется командой `generate --check` на этапе предварительных проверок.

Гейт `check-comment-hygiene.mjs --check` падает при кириллице в любом комментарии исходного кода. Он запускается в `pretest` кодовых репозиториев (core, plugin-sdk, runtime) и в CI-шаге «Comment hygiene», покрывающем все пять репозиториев.

### Слои

Каждый слой комментариев несет только свою информацию.

| Слой | Формат | Обязательно где |
| --- | --- | --- |
| Шапка сгенерированного файла | Шаблон генератора | `*.generated.*` |
| Шапка входного модуля | `/** Module role and format invariant. */` на 1–3 строки | `runtime/src/types.ts`, `plugin-sdk/src/index.ts`, `@osnova/types/src/index.ts` и входные модули пакетов core |
| JSDoc публичной поверхности | `/** What it does and its invariant, if any. */` в одну строку | Экспортируемый API в plugin-sdk на рукописном участке, `preload` с `window.osnova`, публичные интерфейсы SDK. Для обычного экспорта внутри монорепозитория комментарий не нужен, если имя и типы уже объясняют поведение |
| Инлайн-комментарий о причине | `// ...` на 1–2 строки, до 6 строк для security- и protocol-инвариантов | Пять обязательных классов причин из следующего раздела |
| Стрелка в документацию | `// see osnova-docs/docs/adr/adr-0008-runtime-supervisor.md` в одну строку | Рядом с локальной строкой-инвариантом и с квалификатором репозитория. Холостая ссылка без объяснения запрещена |

### Обязательные классы причин

Автор и ревьюер проверяют наличие комментария в следующих случаях:

- Для решений fail-open, fail-closed и молча поглощающих `catch` указывается выбранный дефолт, его причина и причина отказа от противоположного варианта.
- Для решений безопасности, а не для простых фактов, объясняется, почему используется `stdin`, а не `argv`, область `CurrentUser`, режим `0o600`, выбранный класс правил ReDoS, доверие к endpoint-ам или проверка выхода через symlink.
- Происхождение константы сначала выражается именованной константой. Например, `const MAX_VISIBLE_ARTIFACTS = 30`. Комментарий нужен только при неочевидном происхождении: `// Matches the budget in the context policy spec.` Комментарий `// Limit to 30` без причины считается мусором.
- Для протокольных инвариантов и порядка действий объясняются STALE-GUARD эпохи, порядок `log turn before observation` и объединенный `coalesced reindex`.
- Для сознательного дублирования указывается, почему импорт не используется, и дается указатель на контракт. Для `slugify` это векторы проверок в `osnova-spec/contract/slug-vectors.json`.

### Жесткие запреты

- `FIXME`, `HACK` и `XXX` запрещены всегда.
- `TODO` разрешен только в форме `// TODO(osnova-runtime#184): Remove after manifest v1 support is dropped.` Здесь обязательны репозиторий из известного списка, номер задачи и условие удаления. Для репозиториев без дисциплинированного трекера `TODO` полностью запрещен.
- Закомментированный код запрещен. Для архива есть `git`.
- Комментарии, повторяющие код, запрещены: `// increment counter` и `// create the project` не добавляют смысла. Если имя неудачное, его нужно переименовать.
- Декоративные разделители вида `// ===== Section =====` запрещены.
- Минимальная плотность комментариев не устанавливается, потому что такие минимумы порождают мусор. Качество обеспечивается ревью.

### Правило ревью

Неочевидное решение или инвариант должны быть обнаружимы из кода, ближайшего комментария или явно связанного проектного документа. Лучшее исправление часто состоит в улучшении имен, добавлении именованной константы или типа. К комментарию следует обращаться только тогда, когда эти средства не могут передать смысл.

### Эталонные примеры

Хорошие комментарии уже есть в репозитории и используются как эталоны:

```ts
// STALE-GUARD: pin the load epoch. If project/session changed while the
// request was in flight, a slow reply must not overwrite the current timeline.
// SessionWorkspace.tsx:79

// Never hard-link the immutable global cache into an extension-controlled
// directory. A trusted native tool could otherwise mutate the cache bytes.
// operation-service.ts:224

// Unparseable endpoints are classified external so provider validation forces a
// "cloud" recipient declaration. Malformed input must never earn local trust.
// plugin-sdk/src/index.ts: isExternalEndpoint

const MAX_VISIBLE_ARTIFACTS = 30 // Catalog budget. Keeps the compact envelope under the policy ceiling.
```

Плохие варианты и причина нарушения:

- `// create the project` повторяет имя действия.
- `// TODO fix later` не соответствует грамматике `TODO`.
- `const x = 30 // limit` использует неименованное число и не объясняет его происхождение.
- `// ===== helpers =====` является декоративным разделителем.
- `/* old code: if (a) b() */` сохраняет мертвый код.
- `// see osnova-docs/docs/adr/adr-0008-runtime-supervisor.md` без локального инварианта является холостой ссылкой.
