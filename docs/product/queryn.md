# Queryn

## Статус

`Queryn` - принятое целевое направление продукта. Документ является
нормативным вместе с продуктовыми принципами, архитектурными документами и ADR,
которые ссылаются на него.

Существующий файловый MVP сохраняется как совместимый фундамент. Формат проекта
`0.1` остается читаемым, а переход на модель Queryn выполняется явной миграцией в
формат `0.2`.

## Определение

**Queryn - local-first модульная среда для учебных и исследовательских проектов, объединяющая обычные файлы, структурированные знания и подключаемые инструменты.**

В текущей поставке desktop пользователь работает с обычными файлами, заметками,
материалами и сессиями, а `agent.chat` выполняет доступный диалоговый цикл.
Ручные operations доступны через runtime API и CLI. Кодовый `ToolWorkspace` пока
не имеет маршрута из `ProjectNavigator`, поэтому ручная работа через этот экран
остаётся целевой возможностью. Результат становится артефактом только в
operation flow, который публикует его descriptor и provenance. Нативное
редактирование заметок и assets остаётся записью обычных файлов и само по себе
не создаёт артефакт. Целевая модель допускает текстовые, графические, аудио и
другие operation-generated результаты как артефакты проекта.

Короткая формула:

> Материалы превращаются в знания, знания - в проекты, а инструменты помогают работать с ними вручную или через AI.

Главная пользовательская ценность:

> Собрать собственную систему обучения и исследования, не разрывая знания, инструменты и результаты между разными приложениями.

## Основной фокус

Первый и главный сценарий Queryn - обучение и исследовательская работа:

- сбор материалов по теме;
- создание и развитие конспектов;
- проверка понимания;
- поиск связей и противоречий;
- подготовка карточек, объяснений и учебных планов;
- производство производных материалов: аудио, изображений, схем и других
  артефактов.

Встроенные операции текущего runtime работают с `queryn.project.search/read/list`,
`web.fetch`, `artifact.resolve`, `notes.create`, `files.import`, `graph.link`,
памятью сессий и контекстом. Проверка понимания, поиск противоречий, карточки,
объяснения, учебные планы, аудио, изображения и схемы обозначают целевые
сценарии. Линтер материалов существует как справочное или необязательное
расширение, а не как встроенная возможность.

Архитектура может поддерживать более широкие интеллектуальные и творческие
процессы, но продукт не должен начинать как абстрактная универсальная среда.

## Продуктовая модель

### Проект

Проект является local-first контейнером пользовательской работы. В текущей
поставке он объединяет:

- обычные файлы и Markdown-конспекты;
- рабочие сессии;
- подключенные инструменты;
- артефакты, зарегистрированные operation flow;
- связи, записанные доступной relation operation.

Структурированные знания, карточки и графовая поверхность остаются целевой
моделью. Нативные notes и assets не преобразуются в артефакты автоматически.

Папка проекта остается источником истины. Queryn улучшает работу с ней, но не превращает данные в закрытое внутреннее хранилище.

### Сессия

Сессия - отдельная задача, диалог или рабочий процесс внутри проекта. Проект
хранит долговечный контекст, а сессия - текущую цель, сообщения, вызванные
операции и полученные результаты. Явно закреплённый контекст сессии поддерживает
ссылки на артефакты, а выбор материалов из composer пока не реализован.

Пользователь должен воспринимать структуру естественно:

```text
Проект
  Сессия
  Сессия
  Сессия
```

### Инструмент

Инструмент - самостоятельная возможность внутри Queryn. Целевая модель
допускает собственный интерфейс и работу полностью без AI. В текущем desktop
рабочие поверхности проекта и список доступных operations уже работают, а
кодовый путь `ToolWorkspace` пока не имеет доступного маршрута из
`ProjectNavigator`. Поэтому отдельный manual view для каждого расширения ещё не
является общим пользовательским контрактом.

Примеры:

- редактор конспектов;
- файловый менеджер проекта;
- граф знаний как целевой интерфейс;
- линтер материалов;
- TTS-студия;
- генератор изображений;
- средство анализа источников.

TTS-студия, генератор изображений и средство анализа источников здесь описывают
целевые расширения. В текущем runtime встроены операции работы с проектом,
заметками, связями, контекстом и web-fetch, а не эти специализированные
интерфейсы.

Инструмент сам выполняет предметную работу. Агент может только запросить объявленную операцию, если разработчик инструмента явно разрешил агентное управление.

### Артефакт

В текущем runtime артефакт появляется в operation flow, который публикует
типизированный результат и его provenance. Нативная ручная работа с notes и
assets остаётся работой с файлами и не получает provenance артефакта без такого
operation flow.

Целевая модель допускает следующие типы operation-generated артефактов:

- Markdown-конспект;
- файл;
- изображение;
- аудио или видео;
- набор карточек;
- граф или схема;
- диагностический отчет;
- diff;
- пользовательский тип, объявленный расширением.

Набор типов расширяем. Встроенный runtime сейчас через `queryn.notes.create` и
`queryn.files.import` создаёт descriptors для заметок и импортированных файлов,
а `queryn.graph.link` записывает связь между артефактами через relation API.
Генерация карточек, аудио, изображений и схем, а также соответствующие UI,
остаётся целевым слоем расширений.

Для operation-generated артефакта сохраняется связь с проектом, операцией,
запуском и, если они переданы, исходными материалами и сессией. Пользовательские
результаты должны сохраняться в обычных файлах проекта, когда для них существует
переносимый формат.

## Два равноправных режима работы

### Ручной режим

Целевая модель предполагает, что пользователь открывает инструмент, задаёт
параметры и получает результат без участия модели. В текущем desktop
`ToolWorkspace` существует в renderer, но вход из `ProjectNavigator` отсутствует,
поэтому этот путь пока доступен только через runtime API и CLI.

```text
Пользователь
  -> интерфейс инструмента
  -> операция
  -> артефакт
  -> проект
```

Например, целевой Tool может дать пользователю TTS-студию, где он выбирает
конспект и голос, запускает генерацию и сохраняет аудио в проект. TTS-студия не
входит в текущий набор встроенных возможностей.

### Агентный режим

Пользователь формулирует цель в едином поле ввода. В текущем продукте запрос
передаётся через `agent.chat` в единый диалоговый tool-loop `AgentKernel`.
Модель получает историю сессии и схемы доступных operations, вызывает их по
ходу диалога, получает observations и продолжает работу. Risk-операция может
приостановить конкретный вызов до approval. Отдельный структурный `AgentPlan`
и pipeline текущий продукт не создаёт.

```text
Запрос пользователя
  -> история сессии и схемы доступных operations
  -> вызов operation
  -> observation или approval
  -> следующий шаг диалога
  -> финальный текст и operation-generated артефакты
```

AI не заменяет инструменты и не владеет их логикой. Он является одним из способов связать инструменты в понятный пользователю процесс.

## Единое поле ввода

Поле ввода - основной агентный интерфейс, а не единственный способ работы с продуктом.

Через него пользователь:

- формулирует задачу;
- проверяет compact preview проектного контекста;
- выбирает настроенную модель и режим памяти;
- получает потоковый ответ, видимую активность tool-loop и результаты операций;
- подтверждает отдельную risk-операцию, когда runtime переводит её в ожидание.

Выбор и прикрепление конкретных артефактов из composer, отдельное представление
плана и структурированный список источников в финальном ответе являются будущим
развитием интерфейса и контракта. Они не входят в текущую поставку.

Интерфейс контекста должен оставаться компактным. По умолчанию достаточно индикатора вроде `Контекст · 4`. Подробный состав открывается только по запросу пользователя.

Проектный контекст, выбранные артефакты, доступные операции и полные данные инструмента являются разными слоями и не должны безусловно помещаться в один prompt.

## Контекст и AI-поддержка

Инструмент и создаваемый им артефакт не обязаны поддерживать AI.

Для типа артефакта возможны разные режимы:

- `none` - контекст для модели недоступен;
- `automatic` - Queryn использует стандартный обработчик;
- `declarative` - разработчик перечисляет полезные поля;
- `custom` - расширение предоставляет собственный контекстный провайдер.

Контекстный провайдер должен уметь отдавать как минимум два представления:

- компактное - краткие сведения для выбора подходящих источников в tool-loop;
- расширенное - подробные данные по явному запросу и в заданном бюджете.

Эти представления обслуживают выбор контекста для tool-loop, а не отдельный
видимый AgentPlan.

Инструмент, тип артефакта и контекстный провайдер независимы. Один плагин может создавать аудио, а другой - добавлять транскрипцию или анализ этого аудио.

## Расширения

Единый пакет расширения может добавлять несколько вкладов в продукт.

### Theme

Добавляет оформление, токены, иконки и визуальные пресеты. Не требует отдельной среды исполнения.

### Tool

Добавляет интерфейс, операции, типы артефактов или обработчики. Сторонний код не
исполняется в renderer или привилегированном desktop host: он использует
управляемый process, OCI или remote runtime. В текущем релизе `contributes.views`
только валидируется и подготавливается к размещению, а runtime и desktop ещё не
регистрируют и не отрисовывают собственные views расширения. Собственный
интерфейс расширения и доступная ручная поверхность остаются целевой
возможностью.

Базовые возможности Queryn - работа с конспектами и файлами - также следует
рассматривать как инструменты платформы, даже если они поставляются вместе с
приложением. Встроенная `queryn.graph.link` сейчас предоставляет relation API
для записи связей. Полноценные граф знаний и карточки в интерфейсе остаются
целевой возможностью и не входят в текущую поставку.

### Advanced Tool

Добавляет сложную возможность со своей средой исполнения. Advanced Tool может включать:

- отдельный процесс или OCI-контейнер;
- Python или другой runtime;
- локальный HTTP, stdio или MCP-сервис;
- собственную модель и правила ее загрузки;
- требования к памяти, диску, GPU и сети;
- собственный интерфейс и типы артефактов.

Контейнер является способом исполнения, а не пользовательской сущностью. Пользователь устанавливает и открывает инструмент, а не управляет контейнером как основной задачей.

## Управляемые среды исполнения

Queryn должна предоставлять общий Runtime Supervisor, скрывающий конкретный механизм запуска.

Среда Advanced Tool может иметь один из жизненных циклов:

- `job` - запускается для одной операции;
- `project` - работает, пока активен проект;
- `shared` - лениво запускается для нескольких проектов и останавливается после простоя.

При установке Queryn должна явно показывать:

- размер инструмента и моделей;
- требования к памяти и GPU;
- необходимые разрешения;
- сетевой доступ;
- место установки и хранения данных;
- проекты, в которых инструмент включен.

Среда исполнения не должна напрямую изменять папку проекта. Она получает ограниченные входы и возвращает результаты через общий протокол обмена артефактами. Host валидирует результат и только затем сохраняет его в проект.

## Менеджер инструментов

Менеджер инструментов разделяет три состояния:

1. Инструмент установлен в Queryn.
2. Инструмент подключен к конкретному проекту.
3. Среда инструмента запущена сейчас.

В текущей поставке экран Tool Manager устанавливает пакет, подключает или
отключает расширение от проекта и показывает объявленные operations и
permissions без выбора отдельного набора разрешений. Backend имеет отдельные
методы обновления и отката, но экран не предоставляет полного управления
жизненным циклом среды и не запускает отдельный manual view. Поддержка
Developer Mode для явно неподписанных пакетов и подробной настройки grants
остается будущим слоем контроля доверия.

Целевая модель Менеджера инструментов должна дать пользователю возможность:

- устанавливать и удалять расширения;
- видеть тип расширения и его возможности;
- подключать инструмент к проектам;
- управлять моделями и занимаемым местом;
- просматривать разрешения;
- запускать, останавливать и диагностировать Advanced Tool;
- открывать ручной интерфейс инструмента.

Технические детали контейнера или процесса должны находиться в настройках среды выполнения, а не в основном пользовательском потоке.

## Основной цикл продукта

```text
Создать проект
  -> добавить материалы
  -> подключить инструменты
  -> работать вручную или сформулировать запрос
  -> получить результаты операций
  -> использовать их в следующих инструментах и сессиях
```

Артефакты являются целевым способом композиции для результатов, которые
публикуют операции. Инструменты не должны знать внутреннюю реализацию друг
друга: они принимают и возвращают типизированные результаты через стабильный
контракт Queryn.

## Продуктовые принципы Queryn

- Local first: основные данные принадлежат пользователю и находятся в папке проекта.
- Manual first: полезность инструмента не обязана зависеть от AI.
- AI optional: модель оркестрирует доступные возможности, но не является владельцем продукта.
- Artifacts first: operation-generated результаты имеют тип, происхождение и
  долговечное представление, а нативные notes и assets остаются обычными файлами.
- Composable tools: инструменты объединяются через операции и артефакты.
- Explicit permissions: доступ к проекту, сети, моделям, GPU и внешним процессам объявляется заранее.
- Lazy runtimes: тяжелые среды запускаются только при необходимости.
- Inspectable context: текущий desktop показывает компактный preview, а полный
  audit envelope и точная атрибуция источников относятся к следующему слою.
- Graceful degradation: проект и базовые инструменты остаются полезными без плагинов, контейнеров и AI runtime.

## Чем Queryn не является

Queryn не должна превращаться в:

- закрытый редактор заметок;
- оболочку над одной LLM;
- Docker Manager;
- IDE для разработки агентов;
- магазин несвязанных AI-функций;
- систему, в которой плагины произвольно переписывают основу приложения.

## Связь с текущей Queryn

Текущая Queryn уже предоставляет полезный фундамент:

- folder-based проекты;
- Markdown-конспекты;
- обычные файлы;
- связи между материалами;
- desktop shell;
- начальный plugin SDK;
- отдельную границу AI runtime.

Queryn сохраняет этот фундамент, но меняет центр продукта: вместо учебного файлового редактора целевой моделью становится расширяемая среда учебных и исследовательских проектов.

Переход закреплен ADR 0005-0010. Старый ADR 0004 остается частью истории, но его
ограничение плагинов только TypeScript/JavaScript superseded новой моделью
extension contributions и управляемых runtime.

## Граница данных

По умолчанию Queryn индексирует только текущий проект. Внешние каталоги, сервисы
и будущий контекст всего компьютера могут подключаться только как отдельные
источники с явным scope и разрешением пользователя. Наличие такого источника не
меняет папку проекта как источник истины.

## Лицензионная граница референсов

Sentient OS используется как архитектурный референс для incremental connectors,
crash recovery, staging и атомарной публикации. Код под AGPL не переносится в
проприетарный desktop или permissive core без отдельного лицензионного решения.
