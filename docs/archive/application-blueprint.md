# Базовый проект приложения

> Исторический blueprint интерфейса 0.1. Для нового фронтенда нормативна [UX-доктрина Reborn](/product/ux-doctrine); этот документ сохраняется как описание уже реализованной файловой базы.

Этот документ фиксирует стартовую продуктовую структуру desktop-приложения Osnova. Он описывает, какие экраны и функции должны появиться первыми, какие обещания продукт дает пользователю и какие возможности намеренно остаются следующими слоями.

Osnova не должна восприниматься как еще один закрытый редактор заметок. Базовая продуктовая позиция: пользователь создает обычную папку проекта, хранит в ней Markdown-конспекты, вложения, метаданные и результаты работы, а приложение помогает превратить эту папку в понятную рабочую среду.

## Продуктовое обещание

Osnova помогает строить личные проектные пространства из обычных файлов, заметок и материалов, сохраняя контроль над структурой, внешним видом, workflow и будущим AI-контекстом.

Ключевые акценты:

- Данные пользователя с самого начала лежат в обычной папке.
- Markdown является основным форматом текстовых материалов.
- Вложения хранятся рядом с проектом и остаются доступными вне приложения.
- Приложение улучшает навигацию, работу со связями, визуальную организацию и автоматизацию, но не подменяет файловую модель.
- AI является дополнительным слоем поверх проекта, а не обязательным источником истины.

## Пользовательские уровни

### Базовый пользователь

Базовый пользователь должен быстро понять:

- где лежат его данные;
- как создать или открыть проект;
- как создать первый конспект;
- как добавить файл;
- почему проект останется полезным без приложения.

Для этого уровня приложение должно быть спокойным и очевидным. Не следует начинать с плагинов, графа, сложных тем, AI-настроек или подробной схемы экспорта.

### Регулярный пользователь

Регулярный пользователь работает с несколькими проектами и ожидает:

- быстрый вход в последние проекты;
- обзор состояния проекта;
- список конспектов;
- редактирование Markdown;
- вложения и связь файлов с заметками;
- базовую диагностику структуры проекта.

Этот уровень определяет основной MVP desktop-приложения.

### Продвинутый пользователь

Продвинутый пользователь будет настраивать:

- внешний вид workspace и отдельных проектов;
- проектные шаблоны;
- правила наследования оформления;
- расширения;
- будущие AI-контексты и локальную индексацию.

Эти возможности должны быть добавочными. Они не должны усложнять первый сценарий создания и открытия проекта.

## Базовая информационная архитектура

Приложение строится вокруг двух состояний: workspace без открытого проекта и рабочее пространство открытого проекта.

### Workspace

Workspace отвечает за вход в работу.

Основные функции:

- показать последние проекты;
- создать новый проект;
- открыть существующую папку проекта;
- искать по известным проектам;
- хранить глобальные настройки приложения;
- задавать базовую визуальную палитру workspace.

Workspace не должен становиться отдельной базой данных, которая владеет проектами. Он может хранить список последних путей, настройки интерфейса и производное состояние.

### Открытый проект

Открытый проект является главным рабочим пространством пользователя.

Базовые разделы:

- Обзор;
- Конспекты;
- Файлы;
- Связи;
- Настройки.

Будущие разделы:

- Карточки;
- Плагины;
- AI-контекст;
- Автоматизации.

## Базовый набор экранов

### 1. Launch screen

Назначение: создать ощущение цельного продукта до появления рабочей среды.

Требования:

- чистый фон;
- анимация mark-логотипа;
- короткая продолжительность;
- отсутствие интерактивных элементов;
- мягкий переход в workspace.

Launch screen не должен задерживать пользователя дольше необходимого и не должен заменять onboarding.

### 2. Главная workspace

Назначение: дать быстрый вход в проекты.

Содержимое:

- список последних проектов;
- действие создания проекта;
- действие открытия папки;
- состояние пустого workspace;
- короткий локальный статус данных;
- глобальный поиск по известным проектам.

Главная не должна продавать все возможности продукта сразу. Ее задача - быстро вернуть пользователя к работе.

### 3. Создание проекта

Назначение: создать папку проекта с понятной структурой.

Поля и действия:

- название проекта;
- путь хранения;
- тип проекта;
- стартовый шаблон;
- цвет или визуальный акцент;
- предварительный просмотр структуры папки.

Минимальная создаваемая структура:

```text
project/
  osnova.json
  notes/
  assets/
  .osnova/
```

Создание проекта должно объяснять, что папка является источником истины.

### 4. Открытие проекта

Назначение: безопасно открыть существующую папку и показать ее состояние.

Функции:

- выбор папки;
- чтение `osnova.json`;
- проверка минимальной структуры;
- показ ошибок валидации;
- возможность открыть папку в файловой системе.

Если папка не является проектом Osnova, приложение должно объяснить проблему и предложить безопасное действие, не меняя данные без подтверждения пользователя.

### 5. Обзор проекта

Назначение: дать пользователю состояние проекта после открытия.

Содержимое:

- название, путь и тип проекта;
- последние конспекты;
- последние вложения;
- быстрые действия;
- диагностический статус;
- краткая информация о структуре проекта.

Обзор должен быть первым экраном открытого проекта. Он лучше подходит для ориентации, чем немедленный переход в редактор.

### 6. Конспекты

Назначение: обеспечить основную ежедневную работу с Markdown.

Функции MVP:

- список конспектов из `notes/`;
- дерево вложенных папок внутри `notes/`;
- создание конспекта;
- создание папки;
- открытие конспекта;
- редактирование Markdown;
- сохранение в файл;
- отображение базового frontmatter;
- preview Markdown;
- вставка wiki-links на другие статьи;
- поиск по названию.

Следующие функции:

- backlinks;
- теги;
- шаблоны заметок;
- привязка вложений.

### 7. Файлы

Назначение: сделать вложения частью проекта, а не второстепенной папкой.

Функции MVP:

- просмотр файлов в `assets/`;
- дерево вложенных папок внутри `assets/`;
- создание папки;
- добавление файла через drag and drop;
- открытие файла во внешнем приложении;
- открытие папки проекта;
- вставка Markdown-ссылки на файл в текущий конспект;
- отображение связи файла с конспектами, когда такая связь существует.

Следующие функции:

- preview изображений;
- preview PDF;
- группировка по типам;
- привязка файла к текущему конспекту.

### 8. Связи

Назначение: показать структуру знаний без преждевременного усложнения графом.

Функции первого слоя:

- входящие ссылки;
- исходящие ссылки;
- связанные файлы;
- список неразрешенных ссылок.

В MVP связи могут отображаться как список найденных wiki-links и file-links без полноценного графа.

Полноценный визуальный граф является следующим слоем. Он должен появиться после того, как связи станут полезными в списочном виде.

### 9. Настройки проекта

Назначение: управлять проектом как самостоятельной рабочей средой.

Функции:

- метаданные проекта;
- путь проекта;
- визуальный акцент проекта;
- наследование визуальных настроек;
- диагностика структуры;
- экспорт или создание архива;
- открытие папки проекта.

Экспорт не должен подаваться как способ забрать данные из закрытого приложения. Правильная формулировка: данные уже лежат в обычной папке, а экспорт создает переносимое представление или архив.

## Персонализация и наследование

Персонализация должна развиваться постепенно.

Первый слой:

- глобальная палитра workspace;
- цветовой акцент проекта;
- режим наследования от workspace;
- локальное переопределение проекта.

Второй слой:

- визуальные пресеты;
- настройки плотности интерфейса;
- оформление отдельных типов проектов;
- наследование настроек между родительскими и дочерними проектами.

Третий слой:

- проектные наборы плагинов;
- шаблоны workflow;
- автоматизации;
- расширенные правила наследования.

Интерфейс должен явно показывать источник настройки:

- унаследовано от workspace;
- унаследовано от родительского проекта;
- переопределено здесь.

## Markdown и совместимость

Osnova должна быть Markdown-first средой. Совместимость с Obsidian-подобными workflow является важным направлением, но не должна формулироваться как полная совместимость без реализации всех соответствующих деталей.

Корректное обещание:

- обычный Markdown;
- frontmatter;
- wiki-links как направление совместимости;
- вложения рядом с проектом;
- открытая файловая структура.

Не следует обещать полную обратную совместимость с Obsidian, пока не поддержаны реальные особенности такого workflow: соглашения о путях вложений, embeds, heading links, block links, frontmatter conventions и поведение ссылок.

## AI-контекст

AI должен работать рядом с проектом, а не вместо него.

Базовая модель:

- текущая заметка может стать контекстом;
- текущий проект может стать контекстом;
- пользователь видит, какие папки и файлы доступны AI;
- индексы и кеши являются производными данными;
- сохраненный пользователем AI-output становится обычным файлом проекта.

Первый AI-экран не должен быть главным входом в приложение. Лучше начинать с боковой панели или отдельного раздела проекта, где явно показано, что AI видит и что может сделать.

## Non-goals для первого релиза

Первый релиз не должен включать:

- cloud sync;
- marketplace плагинов;
- полную совместимость с Obsidian;
- rich editor;
- перемещение и переименование узлов дерева;
- визуальный граф как основной интерфейс;
- обязательный AI-runtime;
- сложное наследование плагинов;
- полноценный архивный транспорт `.osnp`;
- универсальный менеджер личной информации без рамки проекта.

Эти направления могут развиваться позже, но не должны мешать базовому сценарию: создать проект, писать конспекты, хранить вложения, видеть структуру и сохранять контроль над папкой.

## Рекомендуемый порядок разработки

1. Launch screen.
2. Главная workspace.
3. Создание проекта.
4. Открытие проекта.
5. Обзор проекта.
6. Конспекты: список и редактор.
7. Файлы и вложения.
8. Настройки проекта.
9. Связи и backlinks.
10. AI-контекст.
11. Плагины и расширенная персонализация.

Этот порядок должен сохранять продукт понятным. Каждая новая возможность должна усиливать folder-based workflow, а не переносить источник истины в скрытое состояние приложения.
