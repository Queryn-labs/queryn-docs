# ADR 0016: Среды исполнения и зависимости расширений

## Статус

Принято.

## Контекст

Расширение Queryn может быть простой декларацией темы, процессом на Node.js,
нативной программой, OCI-образом или удалённым сервисом. Эти варианты имеют
разную стоимость запуска, модель доверия и способ доставки зависимостей. Если
host не различает их явно, установка пакета незаметно превращается в изменение
системной среды пользователя, а результат начинает зависеть от глобальной
версии Node.js, Python, Java, системных библиотек, контейнерного движка или
внешней сети.

Текущая основа уже разделяет установку, подключение к проекту и запуск, хранит
версии пакета рядом, проверяет целостность файлов и поддерживает драйверы
`builtin`, `node-process`, `native-process`, `oci` и `remote`. Этого достаточно
для контролируемого запуска заранее подготовленного пакета. Этого недостаточно
для общего обещания, что произвольная зависимость будет установлена,
совместима с платформой и воспроизводимо удалена.

Особенно опасны два неявных допущения. Первое состоит в том, что host может
использовать собственный runtime для любого расширения. Это связывает
расширение с внутренними версиями Queryn и делает обновление приложения
потенциально несовместимым. Второе состоит в том, что расширение может при
первом запуске выполнить `npm install`, `pip install`, загрузить бинарник или
изменить глобальное окружение. Такой путь ухудшает воспроизводимость,
затрудняет удаление и создаёт неконтролируемую границу поставки кода.

Нужна единая политика, которая сохраняет разнообразие инструментов, но делает
их зависимости явными, проверяемыми и ограниченными областью Queryn.

## Решение

### 1. Каждый runtime выбирает один явный класс исполнения

Queryn поддерживает пять классов исполнения.

| Класс | Назначение | Кто поставляет среду |
| --- | --- | --- |
| `builtin` | Возможности, поставляемые вместе с Queryn | Сборка Queryn |
| `node-process` | Переносимые JS и TS инструменты | Пакет расширения и совместимый Node host |
| `native-process` | Самодостаточная программа платформы | Пакет расширения |
| `oci` | Инструменты со сложной системной средой | OCI-образ с закреплённым digest |
| `remote` | Внешний Queryn Tool Protocol или MCP endpoint | Владелец удалённого сервиса |

Расширение может объявить несколько runtime descriptors. Каждый descriptor
выбирает ровно один класс исполнения, а tool, operation, connector, model
provider или preview provider явно ссылается на него через `runtimeId`. Host не
угадывает способ запуска по содержимому архива и не переключает драйвер без
нового решения пользователя или новой версии расширения.

`builtin` зарезервирован для кода, зарегистрированного host-сборкой Queryn.
Сторонний пакет не может объявить `builtin` runtime. Внешняя возможность,
которой не нужен отдельный процесс, всё равно оформляется через поддержанный
публичный драйвер и не получает внутренний обработчик приложения.

### 2. Установка пакета не изменяет глобальную систему

Установщик Queryn не выполняет package manager расширения, не пишет в
глобальные каталоги Node.js, Python или Java и не устанавливает системные
пакеты. Установленная версия является неизменяемой. Все файлы, которые нужны
для запуска, должны входить в проверяемый пакет, находиться в закреплённом
OCI-образе, предоставляться менеджером моделей Queryn или оставаться на
удалённой стороне.

Для `node-process` пакет содержит собранный entrypoint со включёнными
производственными зависимостями и явно перечисленные относительные ресурсы.
Каталог `node_modules` не является переносимым форматом поставки. Lifecycle
scripts и запуск `npm install` или `pnpm install` при упаковке host, установке и
первом использовании запрещены. Host может предоставлять совместимый Node
runtime, но его версия и доступные возможности считаются частью протокола
совместимости, а не неявным свойством desktop-сборки.

Формат пакета ограничивает число файлов, размер отдельного файла, общий
декодированный размер и итоговый объём установки. Поставка содержит перечень
компонентов и лицензий производственных зависимостей. Проверка этих ограничений
выполняется до записи файлов в каталог установленной версии.

Для `native-process` пакет содержит самодостаточные исполняемые файлы для
заявленных сочетаний операционной системы и архитектуры. Динамические
системные зависимости должны быть перечислены и проверены до запуска. Если
такую среду нельзя гарантировать переносимо, расширение использует OCI или
удалённый runtime.

Python, Java и другие языковые среды не становятся отдельными неявными
драйверами. До появления управляемого общего механизма автор поставляет
самодостаточный бинарник, OCI-образ или удалённый сервис. Будущий управляемый
runtime допустим только как адресуемая по содержимому зависимость с версией,
платформой, архитектурой, контрольной суммой, размером, лицензией и правилами
удаления.

Модели не упаковываются в расширение по умолчанию. Их установка и доступность
остаются ответственностью `ModelManager`, потому что модели имеют собственный
жизненный цикл, лицензию, объём и аппаратные требования.

### 3. Совместимость проверяется до первого задания

Манифест и запись установки должны позволять host проверить:

- минимальную и максимальную совместимую версию Queryn
- версию протокола инструмента
- поддерживаемые платформы и архитектуры
- требуемый runtime engine и его диапазон версий
- закреплённую целостность пакета или OCI-образа
- обязательные системные возможности, включая сеть, GPU и контейнерный движок
- объём загрузки, объём на диске и лицензию поставляемых зависимостей

Установка может завершиться сохранением пакета, но подключение и запуск не
считаются успешными, пока эти требования не удовлетворены. Недоступное
расширение получает структурированную причину и не блокирует открытие проекта.

Процессный runtime обязан пройти `initialize` до регистрации как готовый.
Host проверяет версию протокола, идентификатор расширения, заявленные
возможности и ограничения. Ответ `initialize` не является информационным
сообщением, которое можно проигнорировать.

### 4. Жизненный цикл зависимости принадлежит runtime control plane

Состояние не образует одну линейную шкалу. Установка относится к версии пакета
на устройстве, подключение относится к паре проект и расширение, подготовка
относится к runtime descriptor на устройстве, а процесс исполнения относится к
конкретному lifecycle scope.

| Область | Идентичность | Состояния |
| --- | --- | --- |
| Пакет | extension id и version | `discovered`, `installing`, `installed`, `integrity-error`, `incompatible` |
| Подключение | project id и extension id | `disconnected`, `connected`, `blocked` |
| Подготовка | runtime id, version, platform и arch | `not-prepared`, `preparing`, `ready`, `unavailable` |
| Исполнение | runtime id и lifecycle scope | `stopped`, `starting`, `running`, `stopping`, `failed` |

Доступность operation вычисляется из всех четырёх областей вместе с grants и
policy. Один установленный пакет может быть подключён к нескольким проектам с
разными разрешениями. Один подготовленный runtime может безопасно совместно
использоваться несколькими совместимыми версиями только при явном совпадении
адресуемой по содержимому зависимости.

Подготовка может включать загрузку OCI-образа или модели после явного согласия
пользователя. Она не должна происходить внутри `jobs/start`. Длительная
загрузка, проверка и удаление являются отдельными заданиями с прогрессом,
отменой и восстановлением.

Удаление версии освобождает принадлежащие ей данные, если они не используются
другой установленной версией. Общие зависимости с адресацией по содержимому
удаляются только после проверки ссылок. Пользовательские проекты и
опубликованные артефакты не удаляются вместе с расширением.

### 5. Доверие и изоляция зависят от драйвера

Проверка подписи и контрольной суммы подтверждает происхождение и целостность,
но не делает код безопасным. `node-process` и `native-process` остаются кодом,
которому пользователь доверил выполнение на устройстве. Ограничения Node.js
являются дополнительной защитой. Сильная изоляция для сложных или менее
доверенных вычислений требует OCI с ограничениями CPU, памяти, сети, файловой
системы и времени.

Удалённый runtime всегда считается сетевым получателем данных. Передача ему
контекста или артефактов проходит через policy и видимое согласие. Локальный
loopback endpoint не считается автоматически доверенным встроенным runtime.

### 6. Ошибка одной возможности не блокирует проект

Если отсутствует контейнерный движок, несовместима архитектура, не загружена
модель или недоступна сеть, Queryn показывает конкретную причину, возможное
действие и затронутые операции. Материалы, сессии и остальные расширения
продолжают работать. Проектная папка не зависит от установленной среды
расширения.

## Межрепозиторные границы

| Репозиторий | Ответственность |
| --- | --- |
| `queryn-spec` | Схемы платформ, runtime requirements, handshake, ограничений пакета и структурированных причин недоступности |
| `queryn-core` | Общие типы совместимости и проверки контрактов проекта |
| `queryn-sdk` | Типы манифеста, сборка самодостаточного runtime, состав поставки и проверки автора |
| `queryn-runtime` | Установка, подготовка, запуск, контроль ресурсов, удаление и диагностика |
| `queryn-desktop` | Согласие пользователя, прогресс загрузки, состояния доступности и восстановление |
| `queryn-extensions` | Эталонные пакеты для каждого поддержанного класса исполнения |

## Последствия

Положительным последствием становится воспроизводимая установка без
загрязнения пользовательской системы. Queryn сможет объяснить, почему
конкретный инструмент недоступен, оценить загрузку до её начала и удалить
принадлежащие версии данные. Обновление desktop-клиента перестанет неявно
менять среду стороннего расширения.

Стоимость решения состоит в более строгой упаковке и необходимости собирать
платформенные варианты нативных инструментов. OCI остаётся тяжёлой зависимостью
и не подходит как обязательная основа всех расширений. Авторы Python и Java
инструментов до появления управляемых сред должны поставлять самодостаточную
сборку, контейнер или удалённый сервис.

Текущая реализация соответствует решению частично. Драйверы, целостность,
staging и разделение установки с подключением уже существуют. Обязательная
проверка ответа `initialize`, полное описание платформенной совместимости,
отдельная подготовка зависимостей и пользовательский экран их жизненного цикла
остаются работой по реализации.
