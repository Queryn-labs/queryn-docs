# Устав документации

Этот документ задаёт правила для сайта Queryn. Сайт в `queryn-docs` является
каноном продуктовых, архитектурных и ADR-решений. README репозиториев служат
коротким входом в код и ссылаются на сайт, но не заменяют его содержание.

## Источник истины

Нормативные утверждения о поведении продукта, архитектурных границах и
межрепозиторных контрактах хранятся в `queryn-docs`. Открытый формат проекта,
JSON Schema и примеры хранятся в `queryn-spec`. Реализация проверяется в
репозитории-владельце перед обновлением документации.

Если реализация и документ расходятся, автор фиксирует расхождение в задаче,
обновляет документ или явно помечает описываемую возможность как целевую. Нельзя
выдавать план или архитектурную идею за уже работающий пользовательский путь.

## Фронтматтер страницы

Каждая Markdown-страница сайта, кроме README, начинается с машинного контракта:

```yaml
authority: normative
lifecycle: active
```

`authority` показывает силу утверждения:

- `normative` задаёт правило, контракт или ожидаемое поведение
- `informational` объясняет контекст и не является источником обязательного
  решения

`lifecycle` показывает жизнь страницы на сайте:

- `active` участвует в актуальной навигации и описывает действующий контекст
- `archived` сохранена для истории и сопровождается предупреждением темы

Оси независимы. Нормативная страница может быть архивной, если она фиксирует
вышедшее из действия правило. Исторические MVP-документы сохраняют
`authority: normative` и получают `lifecycle: archived`, поскольку фиксируют
бывший продуктовый контракт. Для справочного материала без обязательных
утверждений допустима комбинация `informational` и `archived`.

Тема сайта выводит эту семантику над содержимым страницы. Для действующего
нормативного документа показывается бейдж `Нормативный · Действует`, для
заменённой ADR — бейдж с номером новой ADR, а для архивной страницы — бейдж и
предупреждение. У ADR предупреждение архива не выводится, чтобы не смешивать
жизнь страницы с жизнью решения.

## Жизненный цикл ADR

Для страниц в `docs/adr/` обязательны дополнительные поля:

```yaml
adrStatus: accepted
```

Допустимы значения `accepted`, `superseded` и `rejected`. Для
`adrStatus: superseded` обязательно поле `supersededBy` с номером ADR, который
заменяет решение.

ADR никогда не переносятся в `docs/archive/`. Их путь
`docs/adr/adr-NNNN-kebab-slug.md`, ссылки, номер в журнале решений и поле
`supersededBy` остаются стабильными. `lifecycle` описывает жизнь страницы, а
`adrStatus` жизнь архитектурного решения. Поэтому заменённая ADR может оставаться
активной страницей сайта с предупреждающим бейджем без архивного баннера.

## Структура сайта

Сайт имеет пять содержательных секций и отдельную главную страницу:

- Продукт фиксирует позицию, аудиторию, принципы, UX и последовательность
  развития
- Архитектура описывает процессы, runtime, desktop, расширения и версии
- Разработчику содержит правила участия, политики и материалы для авторов
  расширений
- Спецификация даёт вход в контракт формата проекта из `queryn-spec`
- ADR ведёт журнал долгосрочных решений
- Главная даёт пятиминутный маршрут и глоссарий

Страница должна находиться в секции, соответствующей её читателю и владельцу
решения. Архивный документ не должен конкурировать с действующим документом в
основной части навигации.

## Диаграммы

Mermaid является каноническим форматом диаграмм. Диаграмма размещается рядом с
объясняемым текстом и получает заголовок-якорь. Имена узлов, репозиториев,
модулей и протоколов пишутся на английском, подписи и пояснения на русском.
Каждый блок должен разбираться Mermaid и проходить проверку сборки сайта.

Диаграмма не создаёт новый контракт. Если рисунок показывает поведение системы,
его исходное правило должно быть описано в нормативном тексте или ADR.

## Язык и стиль

Документы пишутся на русском языке. Имена файлов, репозиториев, модулей, CLI,
схем и полей контрактов сохраняются в оригинальном виде. Текст должен быть
конкретным, проверяемым и коротким. Не следует добавлять детали, которых нет в
коде или утверждённом решении.

## Проверка перед публикацией

Автор страницы проверяет:

- фронтматтер и соответствие выбранных осей содержанию страницы
- ссылки на существующие страницы и актуальные пути архивных документов
- соответствие утверждений коду репозитория-владельца
- отсутствие дублирования нормативного правила в README и продуктовых страницах
- разбор всех добавленных Mermaid-блоков
- `pnpm build` в `queryn-docs`

Решение, которое затрагивает несколько репозиториев или меняет долгосрочную
границу системы, сначала оформляется ADR, затем отражается в продуктовых и
архитектурных страницах. Изменение реализации и изменение документации должны
оставаться связанными в одном рабочем потоке.
